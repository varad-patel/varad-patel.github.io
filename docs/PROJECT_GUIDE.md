# How to build one project

Every day of the challenge is one folder, `365projects/<N>/`, served at
`https://varad-patel.github.io/365projects/<N>/`. The list of 365 is `data/challenge.tsv`
(columns: id, section, title, description, concept, skills). Project 1 (`365projects/1/`) is the
reference implementation: read all five of its files before writing a new one.

## The bar

Each page is a small product, not a demo. Someone who has never heard of the idea should be able to
use it in ten seconds and understand it in five minutes.

* **It does what its row says.** Every clause of the "description" column in `data/challenge.tsv` is
  something the visitor can actually do. If the row says "then run 100,000 simulated games", there
  is a control that runs 100,000 games.
* **It shows something on load.** Sensible defaults, a meaningful first result, no empty state.
* **It cannot be broken from the keyboard.** Every input is validated. The page never shows `NaN`,
  `undefined`, `Infinity` or an empty chart without saying why. Bad input gets a `note("bad", ...)`
  that says what to fix.
* **It gives examples.** Anywhere the visitor has to type (a formula, a list, numbers), offer
  presets or example buttons.
* **It can be reset** when state accumulates (games played, items added).
* **It is reproducible.** Randomness comes from `rng(seed)` in the kit. Tests use fixed seeds.
* **It works on a phone** (390 px wide, no sideways scrolling) and with a keyboard (real `<button>`s
  and labelled inputs, results that change announced with `role="status"` where it matters).
* **It is correct.** The maths is the real maths. If you are not sure of a formula, derive it, test
  it against a hand-computed case, or test it against a simulation. Do not approximate silently.
* **It stays responsive.** Long simulations run in chunks (for example with `setTimeout` batches or a
  `ticker`) so the page never freezes for more than a moment.

## Files

```
365projects/<N>/index.html       the page: title, lede, empty #app, and the whole write-up
365projects/<N>/logic.js         the model as pure functions. No DOM, no window. Imports only from ../kit/kit.js or data files.
365projects/<N>/app.js           the interface. Imports the kit and logic.js, calls mount(), builds #app.
365projects/<N>/logic.test.mjs   node:test tests for logic.js
365projects/<N>/meta.json        question, finding, limit, sources, built (see below)
```

`README.md` in the folder is generated by `scripts/build_data.py`; do not write it. Page-specific CSS
goes in a small `<style>` block in `index.html`. Bundled data goes in the folder as an ES module
(`export const DATA = ...`) so tests can import it. No other files.

### index.html

Copy the head and the skeleton from `365projects/1/index.html`. What must stay exactly:

* `<body class="proj" data-day="<N>">`, and `<main class="wrap">` holding a `<header class="p-head">`
  with the `<h1>` and `<p class="lede">`.
* `<section class="tool" id="app" aria-label="...">` with only a `<noscript>` inside. `app.js` fills it.
* Then these sections, each `<section class="p-sec">` with an `<h2>` whose text is exactly:
  1. `One finding` (this one is `<section class="p-sec finding">`): one or two sentences with a
     specific number or result that the tool itself produces. A test must reproduce it.
  2. `The idea`: the PPE concept in plain words. Who raised the question, what the argument is, why
     it matters outside the classroom. Two to four paragraphs.
  3. `How it works`: the method, in full. The equations (use `<p class="eq">`, `<var>`, `<sub>`,
     `<sup>`), what each input means, what the algorithm does step by step, why it is right. Use
     `<h3>` sub-headings. A reader should be able to re-implement the tool from this section.
  4. `What this cannot tell you`: four to six honest limits as a list, each starting with a bold
     phrase. Limits of the model and of the idea, not boilerplate.
  5. `Improvements and extensions`: four to six concrete next steps.
  6. `Data and sources` (optional heading text, use `Sources` if there is no data): real references
     only. **Never invent a citation.** If you are not certain of a year, journal or page, cite the
     work by author and title only, or leave it out.
* The two scripts at the end: `../challenge-data.js`, then `app.js` as a module.
* A `<title>` of the form `Title · 365 projects` and a one-sentence `<meta name="description">`.

### meta.json

```json
{
  "question": "The one question the tool answers, ending with a question mark?",
  "finding": "The same specific finding as on the page, in one sentence.",
  "limit": "The single most important limit, in one sentence.",
  "sources": [],
  "built": "2026-10-10"
}
```

`sources` names datasets only (for example `["World Bank"]`); leave it empty for a project that
computes everything in the browser.

## Writing

Plain and specific. British spelling (the list uses "visualisation", "polarisation"). Sentence case
for headings and labels. No hype, no filler, no emoji, no exclamation marks. Say "the tool" or
"this page", not "we". Numbers in the write-up must come from running the code.

Layout classes (see `kit.css`): `.tool-grid` (controls on the left, output on the right; stacks on
small screens) holding `.controls` and `.out`; `.row` (flex, wraps); `.grid2`; `.panel`; `.stats`;
`.muted`, `.small`, `.mono`. The site's `.btn` and `.btn.primary` style buttons.

Chart rules, already built into `chart()`: colours come from the fixed palette in order (pass
`color: 0..7`, never invent hues; use `"#8a94a3"` for a de-emphasised series and `"#16233b"` for a
reference line); two or more named series get a legend; one y-axis only (two measures on different
scales are two charts); label selectively with `marks` or `endLabel`, never a number on every
point; text is never in a series colour.

If the kit lacks something you need, build it inside your project's `app.js` and say so in your
report. Do not edit the kit.

## Projects that use data

* The page makes no network request. Data is a snapshot bundled as an ES module: `365projects/<N>/data.js`
  for one project, `365projects/data/<name>.js` when several share it.
* The snapshot is written by a script, `scripts/data/<name>.py` (or `.mjs`), that downloads from the original
  open source, applies cleaning rules that are written down in its docstring, and takes `--cache DIR` so a
  second run rebuilds the same file without downloading again. Never paste numbers in by hand.
* Open licences only (public domain, CC0, CC BY, Open Government Licence and the like). Name the source, the
  licence and the date retrieved on the page and in the module. If the only data for an idea is not open,
  use open data that answers a nearby question and say so, or simulate and label it as simulated.
* Keep a module under about 400 KB: fewer columns, rounded values, arrays instead of objects.
* A test checks at least three values against the source, with the source's own figure written in the test,
  and pins every number quoted on the page.
* Say what each figure is: the unit, the year or window it covers, and anything averaged or filled in.

## What the reviews of the first 30 pages found

Every one of the first 30 pages had defects that its builder missed. These are the kinds; check each before
you call a page built.

**Results and wording**

* A verdict word ("same", "never", "more than luck", "cannot flip") needs the exact calculation behind it, not
  a rule of thumb. Test the edges on purpose: ties, exact fits, equal inputs, zero, one item.
* Read every sentence the tool can produce in its small cases: "1 comparisons", "from 100 to 100", "the other
  1 are true", a range printed as "50.0% to 50.0%", "$2 against $2" for 1.80 and 2.20.
* A default is not the visitor's answer. Label placeholders as placeholders, and say in the tool itself (not
  only in the write-up) when numbers are invented, simulated or illustrative.
* Compare against the best trivial rule, not a convenient one (a detector that scores 68% is not beating
  "always say yes" at 69%).
* The finding says which presses reproduce it, and a test reproduces it.

**Input**

* Every text box, number box and file has a limit, and the limit has a message: length, size (refuse a large
  file before reading it), range (1e308 is a number), whole numbers where only they make sense.
* Long unbroken text (a pasted URL, an 80-letter name) must wrap: `overflow-wrap: anywhere`.
* A number box's `step` must allow every value the tool accepts: the kit colours `:invalid` inputs red, so
  `step="0.05"` marks a valid 0.33 red with no message. Use `step="any"` unless only whole numbers are valid.
* Files arrive in other encodings, with other separators, empty, or of the wrong kind.
* Text written to a CSV that starts with `=`, `+`, `-` or `@` is a spreadsheet formula. Guard it.

**Keyboard and screen readers**

* After any press that redraws the tool, focus must land somewhere sensible. It must never fall to `<body>`.
* A live region that changes on every animation frame is noise. Announce the result once, when it is ready.
* Headings inside the tool start at `<h2>`. No empty table headers. Buttons that do the same thing to
  different items say which item ("Delete claim 3").
* Bold or colour alone marks nothing: add words.
* Text drawn in an SVG needs 4.5 to 1 contrast like any other (the smoke test measures it).

**Phones**

* A table wider than 390 px becomes a list or is turned on its side. Results sit near the control that
  changes them; a long tool gets jump links.
* A table that turns into a list must do so whenever its own box is narrower than the table, not only on a
  phone: beside the controls on a tablet or a small laptop the box is 600 to 700 px. Stack it with a container
  query whose width is at least the table's widest natural width, measured with the largest input. The kit keeps
  `th` and `.num` cells on one line (`.tbl .num` outranks a plain `.rt td`), so say `.tbl.rt td` to let them wrap.
  Check by opening every disclosure and sweeping the width (day 35's ten-year table overflowed at 701 to 808 px).
* Equations are broken into lines that fit. A canvas is capped to part of the screen height, or a finger
  cannot scroll past it.
* The smoke test taps every control with a real touch at phone width. A control it cannot reach is a failure.

**Speed and storage**

* Any loop that can run for more than about 50 ms is cut into slices, shows progress and can be interrupted.
  Recomputing 100,000 draws on every slider step is debounced.
* A page that saves to the browser says so, keeps open tabs in step (the `storage` event), exports and
  imports without loss, refuses files from a later version, and warns that browsers may clear saved data.

**Facts**

* Every reference is checked against Crossref, the publisher or the Stanford Encyclopedia: authors, year,
  volume, issue, pages. Every "X showed in 1944" is checked too. Nothing is cited from memory.

## Tests

`logic.test.mjs` uses `node:test` and `node:assert/strict`. Test the model, not the DOM:

* a hand-computed case for every formula;
* the known theoretical result (for example the Monty Hall switch rate converging on 2/3) within a
  tolerance that a fixed seed makes deterministic;
* edge cases and invalid input (empty, zero, one item, extreme values);
* the number quoted under "One finding".

## Check your work

From the repository root:

```bash
node --test 365projects/<N>/logic.test.mjs
node scripts/smoke.mjs <N> --browser all
```

The smoke test loads the page at desktop and phone width in Chromium, Firefox and WebKit (Safari's
engine), fails on any console error, uncaught exception, failed request, missing section, sideways
scroll or `NaN`/`undefined` in the tool, and operates every slider, select, checkbox and button once.
At phone width it then uses the page by hand: Chromium as an Android phone and WebKit as an iPhone tap
every button, slider, tick box, text box and chart with a real touch, and Firefox clicks them with a
mouse. A control that is covered, off the screen or deaf to the tap is a failure.
In Chromium it also runs the axe-core accessibility audit (WCAG 2.1 A and AA) on load, after use and at
phone width, and measures the contrast of text drawn in SVG; any violation is a failure. It saves
screenshots to `.smoke/`:
`00N-app.png` (the tool at load), `00N-app-after.png` (after every control was used),
`00N-app-phone.png`, `00N-desktop.png` and `00N-phone.png` (whole page). **Open them and look.** Check
for overlapping labels, clipped text, a chart with the wrong scale, an ugly default, anything you
would not ship. To capture a particular state:

```bash
node scripts/smoke.mjs <N> --eval "document.querySelector('#app button').click()"    # writes .smoke/00N-eval.png
```

A project is built when both commands pass, the screenshots look right at both widths, and the
write-up is complete. It is then reviewed by someone who did not build it, following
`docs/REVIEW_CHECKLIST.md`: every feature used on purpose, the numbers recomputed independently, every
fact and reference checked against a source, keyboard and screen-reader access checked. Only then is it
published. `scripts/build_data.py`, the thumbnail and the commit are done afterwards for the whole
batch (see `CLAUDE.md`).
